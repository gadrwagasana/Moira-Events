# Moira Events Website — Setup

## Run locally

```bash
npm install

# Start a local Postgres database (first time, or after a reboot):
npx prisma dev start moira-events

npm run dev
```

Visit http://localhost:3000

The repo already has a `.env` with `DATABASE_URL` pointed at the local `prisma dev` instance, plus placeholder `ADMIN_PASSWORD` / `ADMIN_SESSION_SECRET` / `CLIENT_SESSION_SECRET` values — change those before deploying (see below).

### Database commands

```bash
npx prisma dev start moira-events   # start the local Postgres instance
npx prisma migrate dev              # apply schema changes (creates a migration)
npx prisma db seed                  # re-seed wedding types / service catalogue
npx prisma studio                   # browse the database in a GUI
```

## Production build

```bash
npm run build
npm start
```

## Required before launch

1. **Production database**
   - The local `npx prisma dev` instance is for development only — it does not survive a server restart/redeploy in production.
   - Point `DATABASE_URL` at a hosted Postgres connection string instead (Neon, Vercel Postgres, or Prisma Postgres cloud — `npx prisma init --db` provisions the latter).
   - Run `npx prisma migrate deploy` against it once, then `npx prisma db seed` to load the wedding types and service catalogue.

2. **Admin login**
   - Set real, unique values for `ADMIN_PASSWORD` and `ADMIN_SESSION_SECRET` in the production environment (currently placeholders in `.env`).
   - Admin dashboard lives at `/admin/enquiries` (redirects to `/admin/login` if not signed in). This is a single shared password for now — no individual staff accounts yet.

2b. **Client Portal login**
   - Set a real, unique value for `CLIENT_SESSION_SECRET` in production — it must be **different** from `ADMIN_SESSION_SECRET` (admin and client sessions are deliberately never interchangeable; see "Client Portal" below).
   - **No email delivery is configured yet.** Client portal accounts are created via an admin-generated invite link that must currently be copied and sent manually (see below) — wiring up real email delivery for these is the main production gap before this feature is client-ready at scale.

3. **Form delivery (Request a Quote / Contact / Book a Consultation / Weddings)**
   - All of these now save directly to the database instead of emailing via a third-party service — no setup required. Quote requests and Contact messages appear in `/admin/enquiries`; consultation requests are stored in the `Consultation` table (no admin screen for those yet — browse via `npx prisma studio` in the meantime).

4. **Logo**
   - The official logo is live (`public/images/moira-events-logo.png`, rendered via `components/Logo.tsx`). The original full-resolution file is also kept at the project root (`Moira Event logo.png`) for reference/future re-exports.

5. **Photography**
   - All image areas currently show styled placeholder blocks ("Photography coming soon"). Replace `components/PlaceholderImage` usages with real `<Image>` components once event photography is available.

6. **Brand colors & fonts**
   - Current palette (`app/globals.css`, under `@theme`) is a placeholder derived from the logo's tones. Update once official brand guidelines are confirmed.

7. **Content marked TBD**
   - Physical office address, social media URLs, pricing/packages, and portfolio case studies are intentionally left as "coming soon" — see the sitemap discovery doc for the full list.
   - Wedding service categories (Planning, Coordination, Venue, etc.) are a proposed grouping, not yet confirmed by the owner — editable via `prisma/seed.ts` or directly in the database.

## Commerce architecture progress

- **Wedding types & service catalogue**: admin-configurable via the `WeddingType`, `ServiceCategory`, and `Service` tables (`prisma/schema.prisma`) — Wedding, Party, and Corporate services are all seeded. Currently edited by re-running `prisma/seed.ts`; a proper admin CRUD UI for these is a planned follow-up.
- **Enquiry sources**: every public submission form (Weddings' 6-step wizard, the general Party/Corporate/Other quote form at `/request-a-quote`, Contact, and Book a Consultation) saves to the database via a shared helper (`lib/enquiries/createEnquiry.ts`). Weddings, Parties, Corporate Events, and Contact all create `Client` + `Event` + `Enquiry` rows visible in `/admin/enquiries`; consultation requests create `Client` + `Consultation` rows (no admin screen yet — planned follow-up).
- **Admin enquiry management**: `/admin/enquiries` supports search (name/email/reference) and filtering by event type and status; `/admin/enquiries/[id]` shows full client/event detail, other enquiries from the same client, and an internal follow-up timeline (call/WhatsApp/email/note entries) via the `Communication` table.
- **Quote management (Stage E)**: `/admin/enquiries/[id]` has a "Create Quote" action that inherits client/event/services from the enquiry without modifying it. `/admin/quotes` (search/filter by status) and `/admin/quotes/[id]` (the quote builder — line items from the catalogue or custom, discount/tax, client vs. internal notes, terms, issue/expiry dates, status lifecycle with a minimum-viable revision history) are live. Quote status changes keep the parent enquiry's status in sync automatically.
- **Booking management (Stage F)**: once a quote reaches `ACCEPTED`, `/admin/quotes/[id]` shows "Create Booking". The booking *snapshots* the agreed commercial state (client, event date/location/guests, wedding type, services, total, currency, accepted quote version) into its own columns/rows rather than reading them live — later edits to the service catalogue, Event, or Quote never retroactively change an existing booking. `/admin/bookings` (search/filter) and `/admin/bookings/[id]` (status lifecycle with validated transitions and a status history log, planning notes, a non-blocking same-date warning) are live. `Booking.quoteId` is DB-unique, so a quote can only ever produce one booking.
- **Payment management (Stage G)**: `/admin/bookings/[id]` has a Payments section — financial summary (Agreed Amount / Total Paid / Outstanding Balance, derived from the payment ledger, never stored redundantly), an overpayment warning when total paid exceeds the agreed amount (shown for manual review only — never auto-resolved into a refund/credit decision), payment history, and a "Record Payment" form (amount/currency/method/reference/date/status/notes — status defaults to Pending, never silently becomes Paid). `/admin/payments` (search/filter) and `/admin/payments/[id]` (full detail, refund fields, audit trail, status history) are live. Payment method stays free text (no hardcoded provider list); no payment gateway is integrated — `provider`/`providerTransactionId` (unique, for future webhook idempotency)/`providerEventId` exist on `Payment` only as groundwork. No client-facing payment page, currency conversion — all explicitly deferred; the schema is ready for them.
- **Invoice management (Stage H)**: `/admin/bookings/[id]` has an Invoices section (separate from Payments) with a "Create Invoice" button — a booking can produce more than one invoice (`Invoice.bookingId` is intentionally not unique), so this is never gated the way "Create Booking" is. Invoice creation snapshots the booking's agreed services (`BookingService`, itself already a frozen snapshot of the accepted quote) into `InvoiceItem` rows — it never reads the live Service catalogue or the original Quote, so editing either afterward can't retroactively change an existing invoice. While an invoice is `DRAFT`, its items, discount, tax, notes, terms, and dates are editable (`/admin/invoices/[id]`) and totals (`Total = Subtotal − Discount + Tax`, clamped to never go negative) recompute automatically; once issued, those fields become read-only — a mistake is corrected by transitioning the invoice to `VOID` and creating a new one, never by silently rewriting an issued document. Status lifecycle: `DRAFT → ISSUED → {PARTIALLY_PAID, PAID, VOID, CANCELLED}`, each transition logged to `InvoiceStatusHistory`. **`PAID`/`PARTIALLY_PAID` are admin-chosen transitions, not automatically derived from payments** — same principle as Booking status in Stage G. The invoice's Payment Summary (Total Paid / Outstanding / status) is *derived*, read-only, and reuses the existing Stage G payment ledger directly (`computePaymentSummary(invoice.total, booking.payments)`) rather than a second ledger or a per-invoice payment-allocation scheme; when a booking has more than one invoice, every invoice shows the same booking-wide paid/outstanding figures, with an explicit on-page note that payments aren't split per invoice. `/admin/invoices` (search/filter) lists every invoice across all bookings. Invoice numbers use the same shared reference scheme (`MI-YYYYMMDD-XXXX`), a separate namespace from quote/booking/enquiry/consultation numbers. Not built this stage (explicitly out of scope): PDF generation/download, client-facing invoice access, VAT/tax rate rules, deposit/installment rules, currency conversion, credit notes, accounting integration, automatic invoice emails/reminders.
- **Consultation management (Stage I)**: `/admin/consultations` (search/filter by status) and `/admin/consultations/[id]` are live. `Consultation.preferredDate` stays exactly what the client originally asked for; a separate `scheduledDate` field holds what admin actually confirmed/rescheduled to, so the original request is never lost. Rescheduling (`rescheduleConsultation`) is independent of status — it only moves `scheduledDate` (optionally updates `method`) and is blocked once a consultation is `COMPLETED`/`CANCELLED`. Status lifecycle is `REQUESTED → {CONFIRMED, CANCELLED}`, `CONFIRMED → {COMPLETED, CANCELLED}`, both terminal states final; every status change and every reschedule is logged to `ConsultationStatusHistory` (same audit-trail pattern as Booking/Payment/Invoice). No calendar/scheduling-conflict view yet — planned follow-up.
- **Client Portal (Stage: Client Portal Foundation)**: authenticated clients can view (read-only) their own event, accepted quote, invoices, and payment history at `/portal/*` — completely separate from admin.
  - **Account creation**: no self-service signup, since there's no email infrastructure to verify an email belongs to the person requesting it. Instead, admin generates a one-time invite link from the "Client Portal Access" card on `/admin/bookings/[id]` ("Generate Invite Link" button), copies the shown `/portal/activate?token=...` URL, and sends it to the client manually (WhatsApp, email, phone — whatever's already used). The client opens it and sets their own password. The link expires after 7 days; the same button, clicked again, generates a fresh one — this doubles as the password-reset mechanism until a real "forgot password" email flow exists.
  - **Authentication**: a client logs in with email + password at `/portal/login`. Passwords are hashed with Node's built-in `crypto.scrypt` (no new dependency). Sessions are a stateless signed cookie (`client_session`, 14-day expiry) — the same approach as admin's `admin_session`, but signed with a **separate** secret (`CLIENT_SESSION_SECRET`) so a client session token can never be forged into, or confused with, an admin one, and vice versa. `proxy.ts` gates both `/admin/:path*` and `/portal/:path*`, each checking only its own cookie.
  - **Ownership / IDOR protection** — the important part: every portal data loader (`lib/client-portal/data.ts`) takes the authenticated client's id (derived from the session, never trusted from a URL/form) and scopes its Prisma query through the ownership chain client → booking → (quote/invoice/payment). A client requesting another client's invoice/booking id gets a 404, not an error that reveals it exists. This was explicitly tested both directions (Client A denied access to Client B's data and vice versa) — see verification below.
  - **Internal data is never returned to the portal**: every loader uses an explicit `select` whitelist, structurally excluding `internalNotes`, `planningNotes`, `createdBy`/`updatedBy`, payment `provider*` fields, every `*StatusHistory` table, and `QuoteRevision` — not just hidden in the UI.
  - **Routes**: `/portal/login`, `/portal/activate` (public); `/portal/dashboard`, `/portal/event`, `/portal/quote`, `/portal/invoices`, `/portal/invoices/[id]`, `/portal/payments`, `/portal/profile` (protected).
  - **Scope decisions**: "My Quote" shows only the Quote actually attached to a Booking (by Stage F's rule, that can only be an ACCEPTED quote) — a client never sees a pre-booking DRAFT/SENT quote this stage. The dashboard/My Event page highlights one "primary" booking (soonest upcoming, falling back to most recent) — the data layer still supports multiple bookings per client and multiple invoices per booking (no new one-per-client/one-per-booking restriction was added); a multi-booking switcher UI is a clean follow-up, not built yet. This stage is read-only — no Accept Quote/Request Changes actions (a separate future stage).
  - **Not built this stage**: real email delivery for invites, a "forgot password" self-service flow, login rate-limiting (same gap as admin login today), a multi-booking switcher UI, any client-facing write actions beyond their own profile/password.
- **Event Planning & Collaboration (Stage J)**: the Booking is now an operational workspace, not just a commercial record. `/admin/bookings/[id]` gained four sections (Timeline, Tasks, Vendors, Planning Notes — jump-link bar at the top of the page) plus two new top-level admin screens, `/admin/tasks` (staff-wide task dashboard: search/filter by status/priority/overdue) and `/admin/vendors` + `/admin/vendors/[id]` (a reusable vendor directory — a vendor can be linked to many bookings via the `BookingVendor` join table, and is **archived** rather than hard-deleted once it has booking history).
  - **New models**: `EventTimelineItem`, `Task`, `VendorRecommendation`, `BookingVendorRecommendation`, `PlanningNote` — all purely additive, hanging off `Booking.id`, and never read or written by any financial calculation (explicitly verified: Quote/Booking.agreedTotal/Invoice/Payment amounts are untouched by every Stage J action).
  - **Status lifecycles**: `EventTimelineItem.status` (`PLANNED→IN_PROGRESS→COMPLETED`, or `CANCELLED`), `Task.status` (`TODO→IN_PROGRESS→COMPLETED`, or `CANCELLED`, with `COMPLETED` reopenable back to `IN_PROGRESS`) — each has its own transition map (`lib/timeline`, `lib/tasks`) enforced server-side, same pattern as every other status field in this app. None of these are ever auto-transitioned by another action. `Task.completedAt` is set/cleared automatically alongside status, not a separate rule. A `TODO` task can be deleted; once it moves on, it must be `CANCELLED` instead (preserves history).
  - **Vendor Recommendations — not vendor contracting.** Moira Events recommends trusted vendors to clients; it does not book, confirm, pay, or otherwise manage a commercial vendor engagement. `VendorRecommendation` (the catalogue: name/category/description/contact info, `active` instead of deleted once it has booking history) and `BookingVendorRecommendation` (a booking's recommendation of one catalogue vendor) deliberately have **no status field at all** — no "confirmed," "booked," "contracted," or "paid." A recommendation only ever carries a `serviceDescription`, internal `notes`, and a `clientVisible` flag. The same catalogue vendor can be recommended to any number of bookings without duplicating the record (verified: one vendor recommended to two independent bookings, each with its own visibility/notes, catalogue record unduplicated). `/admin/vendors` (list/search/filter by category, create) and `/admin/vendors/[id]` (edit, archive/reactivate, see every booking it's been recommended to) are explicitly framed in their UI copy as a recommendation catalogue, not procurement.
  - **No per-status-change history table** for Timeline/Task/PlanningNote/vendor recommendations (unlike the financial records in Stages F–H) — a deliberate scope decision, since this is lower-stakes operational data; `createdBy`/`updatedBy`/`updatedAt` on each row is the traceability level. `EventTimelineItem.type` and `VendorRecommendation.category` are free-text fields with `<datalist>` suggestions, not enums, so staff aren't boxed into a fixed taxonomy.
  - **Client visibility** — every one of the four booking-scoped models (`EventTimelineItem`, `Task`, `BookingVendorRecommendation`, `PlanningNote`) carries a `clientVisible` boolean, defaulting to `false`. Admin explicitly opts a row in; nothing is exposed to the Client Portal by default. `/portal/event` (already built in Stage I) shows four additional sections (Timeline/Tasks/Recommended Vendors/Planning Notes) sourced from four loaders in `lib/client-portal/data.ts` that filter on `clientVisible: true` **and** the existing ownership chain (`booking: { clientId }`) — same IDOR-safe pattern as every other portal loader, verified with a full cross-client test matrix (Client A denied every one of Client B's timeline items/tasks/vendor recommendations/notes, and vice versa) plus a visibility matrix (internal rows never reach the client loaders even for the owning client). Client-visible tasks never expose `priority`/`assignedTo`; client-visible vendor recommendations never expose the internal `notes` field.
  - **`assignedTo` (Task) stays free text** — there's still no staff/user-accounts system in this app (same single shared admin password from Stage D), so this is designed to accept a real assignee relation later without a reshape.
- **Client Collaboration & Planning Requests (Stage K)**: clients can ask Moira Events questions or request changes through the portal — **a request is data, not an instruction**. `/portal/requests` (list + "Submit Planning Request" form) and `/portal/requests/[id]` (thread + follow-up) on the client side; `/admin/planning-requests` (list/search/filter) and `/admin/planning-requests/[id]` (thread + respond + status/priority controls) on the admin side, plus a "Planning Requests" section on `/admin/bookings/[id]`.
  - **New models**: `PlanningRequest` (`bookingId`/`clientId` set once at creation from the session — never trusted from a form — `subject`/`message` hold the client's original ask, `status`, `priority` reusing the existing `TaskPriority` enum rather than a duplicate) and `PlanningRequestMessage` (the thread: `senderType` `CLIENT`/`STAFF`, one row per reply after the original). The original message is never duplicated into a message row — the thread view synthesizes it as the opening entry.
  - **Status lifecycle**: `OPEN→{IN_REVIEW,CANCELLED}`, `IN_REVIEW→{RESPONDED,CANCELLED}`, `RESPONDED→{IN_REVIEW,RESOLVED,CANCELLED}`, both `RESOLVED`/`CANCELLED` terminal (`lib/planning-requests/transitions.ts`, enforced server-side, invalid transitions silently rejected — verified). **Posting a staff response never auto-changes status** — same explicit-action-only discipline as every other status field in this app; a client follow-up is blocked once a request is `RESOLVED`/`CANCELLED`.
  - **Business/financial isolation is the whole point of this stage** — explicitly verified: creating, responding to, and resolving a "change guest count from 100 to 150" request never touches `Booking.estimatedGuests` (confirmed still `100` afterward, both via direct DB check and live on the admin booking page), and a full before/after snapshot of `Booking.eventDate`/`location`/`agreedTotal`, `Quote.totalAmount`, `Invoice.total`, and every `Payment.amount` came back byte-identical. Only an explicit, separate admin action (editing the Booking/Quote/Invoice/Payment directly, unrelated to this stage) can ever change those fields.
  - **IDOR**: both the admin-side list (no ownership scoping — admin sees everything, like every other admin list) and the client-side loaders (`getPlanningRequestsForClient`/`getPlanningRequestDetailForClient`, scoped by `clientId` directly) were tested with two independent clients — Client A denied Client B's request both via direct loader calls and live over HTTP (`/portal/requests/[B's id]` → 404 for Client A's session), and symmetrically for B against A.

## Client registration, verification & password reset (Stage K.5)

Client auth now has three entry paths, all producing the same kind of session:

1. **Admin invite** (unchanged in spirit, hardened in storage) — the "Generate Invite Link" button on `/admin/bookings/[id]` still works exactly as before, but the token is now **hashed at rest** (`Client.inviteTokenHash`). The raw link is shown to admin **exactly once**, immediately after clicking the button (carried via a one-time redirect query param) — it cannot be re-displayed later; regenerating is the only way to get a fresh link, which also doubles as the password-reset mechanism. Activation now also sets `emailVerifiedAt` automatically (an admin-sent invite to a known address is itself sufficient proof of ownership).
2. **Public self-registration** — `/portal/register`. A new client sets a password immediately but cannot log in until they verify their email (`/portal/verify-email?token=...`, sent via the dev email writer described below). If the submitted email already belongs to an existing Client record with **no** password yet (e.g. a prospect from an enquiry), that same record gets the password — never a duplicate row — gated behind the identical verification step. If the email already has an **active** account, registration silently no-ops (no duplicate, no email sent) but the browser sees the exact same generic "check your email" response either way — this is what prevents account-enumeration and unauthorized account takeover via email-guessing (see `app/portal/register/actions.ts` for the full reasoning).
3. **Forgot / reset password** — `/portal/forgot-password` → `/portal/reset-password?token=...`. Always the same generic response regardless of whether the email exists. Reset tokens expire in 1 hour and are single-use (cleared immediately on success); a reused or expired token fails closed with a clear recovery path (request a new one).

All three token types (invite, email-verification, password-reset) are stored **hashed** (`crypto.createHash("sha256")`, see `lib/client-portal/tokens.ts`) — never raw — and are single-use by design (the hash column is nulled the moment the token is consumed, so even a leaked token can't be replayed).

**Migration note**: adding `emailVerifiedAt` meant every client who already had a password *before* this stage shipped would otherwise be locked out by the new "must be verified to log in" check. A one-time backfill (`emailVerifiedAt = now()` for every `Client` row with a `passwordHash` and no `emailVerifiedAt`) was run against the dev database to fix this — **run the same backfill once against any other environment before deploying this stage**, or existing activated clients will be unable to sign in.

**Known limitations, documented rather than silently skipped:**
- **No real email provider is wired up.** `lib/email/send.ts` is a provider-agnostic `sendEmail({to, subject, html, text})` function; right now it writes a readable `.html` file to a local `.local-emails/` folder (git-ignored-equivalent — this repo has no git) and logs the path, so you can actually open and read a "sent" email during development. Wiring a real provider (Resend, Postmark, SES, etc.) later is a one-function change — the call sites never need to change.
- **Rate limiting is in-memory and single-process** (`lib/rate-limit.ts`) — applied to client registration, login, resend-verification, and forgot-password. It resets on every server restart and does **not** hold across multiple instances or serverless cold starts. Fine for a single `next start` process; needs a real store (Redis, etc.) before a multi-instance production deploy.
- **Password reset does not forcibly invalidate already-issued sessions.** The reset token itself is correctly single-use/hashed/expiring (so a compromised token can't be replayed), but an existing signed session cookie from *before* the reset remains valid until its own 14-day expiry. True forced invalidation would require a stateful check on every request (e.g. a session-version column), which was judged not worth the architecture change this stage — flagged here rather than silently assumed.
- **Staff/admin authentication is unchanged** — still the single shared `ADMIN_PASSWORD` from Stage D, deliberately not touched this stage (only the login page copy changed, to read "Moira Events Staff Portal"). A real per-staff-member identity system is a separate future stage.

New env var: `NEXT_PUBLIC_APP_URL` (e.g. `http://localhost:3000` in dev) — every link inside an outgoing email is built from this, never from `localhost`, a hard-coded domain, or a request header. **Set it to the real production domain before deploying.**

## Document generation & PDFs (Stage L1)

Staff and clients can now download a formatted PDF for the three document types that already existed on screen — **nothing new is computed for this stage; the PDF layer only formats fields that are already stored.**

- **New dependency**: `@react-pdf/renderer` — renders a React component tree to a PDF buffer in plain Node (no headless-browser dependency, so it works in any standard server/serverless runtime).
- **Routes** (all `GET`, read-only, `Content-Disposition: inline` so one link both previews and downloads):
  - Admin: `/admin/quotes/[id]/pdf`, `/admin/invoices/[id]/pdf`, `/admin/bookings/[id]/pdf` — gated the same way as every other admin page (`proxy.ts`'s `/admin/:path*` matcher).
  - Portal: `/portal/quote/pdf`, `/portal/invoices/[id]/pdf`, `/portal/event/pdf` — gated by the same `/portal/:path*` matcher, with ownership re-checked inside each document builder via the existing Stage I ownership-scoped loaders (ownership-checked all the way down, nothing new invented).
  - A "Download ... PDF" link was added to each of the six corresponding on-screen pages.
- **`lib/documents/`** — one builder module per document type (`quote.ts`, `invoice.ts`, `booking.ts`), each exposing an `...ForAdmin(id)` and an `...ForClient(clientId, ...)` function that both funnel into a single private mapper per type. That mapper's input type deliberately only declares client-safe fields (no `internalNotes`/`planningNotes`/etc.) — since both the richer admin loader result and the narrower portal loader result satisfy that same structural type, internal fields are unreachable from the mapper by construction, not just filtered at runtime. Presentation-only helpers live in `types.ts`/`format.ts`/`pdf-styles.ts`/`footer.tsx`; the three `*-pdf.tsx` files are the actual `<Document><Page>` component trees; `render.ts` has the one shared `createPdfResponse(element, filename)` call site.
- **Snapshot-safe by construction**: Quote/Invoice/Booking PDFs read `QuoteItem`/`InvoiceItem`/`BookingService` rows directly — never the live `Service` catalogue — so renaming a service afterward never changes a previously-generated document's content (verified: rename a service referenced by an existing Quote/Invoice/Booking, regenerate, confirm the PDF still shows the old name).
- **Idempotent and side-effect-free by construction**: every function in the PDF path is a pure read → format → render; no record is created or mutated, so downloading the same document any number of times never creates a duplicate row (verified: 5x repeated calls against the same Quote/Invoice/Booking, row counts unchanged throughout).
- **Not built this stage** (explicitly out of scope, same spirit as every other stage's deferred list): no stored/versioned document repository, no automatic emailing of a generated PDF, no accounting/tax-engine/VAT/currency-conversion logic, no general read-event audit log.

### A note on the local dev database

`npx prisma dev` (the local embedded Postgres used for development) is an experimental tool and has occasionally needed a full restart during this project's development — symptoms look like `P1017: Server has closed the connection` or `Connection terminated unexpectedly` on queries that touch several relations at once, even though the data itself is fine. If you hit this: `npx prisma dev stop moira-events && npx prisma dev start moira-events`, then restart `npm run dev` so it picks up a fresh connection pool. This hasn't been observed against real hosted Postgres (Neon, etc.) — only this local dev tool under sustained use.

## Email notifications & secure document delivery (Stage L2)

Staff actions that should reach a client now actually send an email: issuing a quote, confirming a booking, issuing an invoice, and replying to a Planning Request. Client invitations (Stage K.5) are now emailed too, in addition to the existing one-time on-screen link.

- **Provider**: `lib/email/send.ts`'s `sendEmail()` is unchanged in shape (provider-agnostic) but now returns a result (`{ok:true, providerMessageId?}` or `{ok:false, error}`) instead of `void`, and accepts an optional `attachments` array. Without `RESEND_API_KEY` set, it still falls back to writing a readable `.html` file to `.local-emails/` (same dev-mode behavior as Stage K.5) — no real email is ever sent locally unless you explicitly configure a key. With it set, it sends via [Resend](https://resend.com) using `EMAIL_FROM_ADDRESS` as the From header.
- **Attachments, not links**: quote/invoice/booking emails attach the actual generated PDF (reusing Stage L1's builders and a new `renderPdfBuffer()` export from `lib/documents/render.ts`) rather than linking to a downloadable URL. These PDFs are small (under 100KB), and attaching avoids introducing any new public/token-based URL surface at all — there's nothing to secure because there's no new link.
- **Delivery tracking (`EmailDelivery` model)**: every quote/invoice/booking/invitation/planning-response send is recorded — type, recipient, related record, status (`PENDING → SENDING → SENT`/`FAILED`), provider message id, attempt count, and a sanitized error message. A small "Last sent ... — Sent/Failed" line appears next to each Send button and on the planning-request detail page, reading the latest matching row. **Not built this stage**: a dedicated `/admin/emails` list across all deliveries — the per-record status line was judged sufficient for now.
- **Duplicate-send prevention**: each Send button embeds a fresh server-generated `requestId` in a hidden field on every page load. The idempotency key (`type:recordId:requestId`) is enforced with a real unique database constraint — the action attempts the send and catches the constraint violation, rather than checking "does this exist?" first (which would be a race under a fast double-click). A genuine resend (after the page reloads with a new `requestId`) is always allowed; only the literal same click/retry is deduplicated. Planning-request responses use the newly-created message's own id as the key instead, since a real new reply only ever creates one row.
- **`EMAIL_VERIFICATION` and `PASSWORD_RESET` are NOT tracked by this new delivery/idempotency system** — those already have their own single-use, expiring tokens and existing rate-limiting (`lib/rate-limit.ts`), which solve the same problem a different way. This is a deliberate scope decision, not an oversight.
- **Known limitation carried over from Stage K.5, now more visible**: `generateClientPortalInvite` still rotates `inviteTokenHash` on every call with no idempotency of its own. A double-click mints two tokens, silently invalidating whichever one was just shown/emailed. The new email layer can't fix this — it only prevents the *same* click from sending two emails, not an admin's second distinct click from generating a second token. A proper fix changes invite-generation semantics and is out of scope for this stage.
- **Security**: all three document-send actions and the invite action are staff-only (same `proxy.ts` `/admin/:path*` gate as every other admin action) — there is no client-reachable path that can trigger sending someone else's document. Internal notes/planning notes are structurally excluded from every template the same way Stage L1's PDFs exclude them (the document builders' input types never declare those fields). HTML in email bodies is escaped (`lib/email/escape.ts`); a client-controlled string placed in a *subject line* (the Planning Request's own subject) is separately stripped of control characters, since HTML-escaping alone doesn't address subject/header injection.

## Document storage & audit trail (Stage M)

Two new metadata-only tables (no PDF bytes stored — Stage L1's on-demand regeneration already works): `AuditEvent` (a generic, cross-entity action log) and `DocumentRecord` (one row per generated PDF: type, reference number, version, filename, size, SHA-256 checksum, and the actor who generated it).

- **Findings from the pre-implementation audit**: before this stage, the only history tracking in the app was four narrow `*StatusHistory` tables (Booking/Payment/Invoice/Consultation), each logging only that one entity's own status transitions — no cross-entity audit trail existed, and nothing recorded document generation/download at all. Stage L2's `EmailDelivery` model already fully covers email delivery attempts/outcomes, so Stage M only *links to* it (via `AuditEvent.correlationId`), never duplicates it.
- **No admin/staff identity system exists.** Admin auth is a single shared password with no per-user accounts — every `AuditEvent` for a staff action is attributed to the literal string `"admin"` (the same placeholder already used throughout this codebase's `createdBy`/`changedBy` columns), never a specific person. Client-initiated actions (creating a planning request, adding a follow-up message) carry a real `Client.id` instead, since client accounts do have real per-account identity.
- **Audit immutability is an application-level guarantee only.** No code anywhere calls `prisma.auditEvent.update()` or `.delete()` — but this is not enforced by Postgres itself (no restrictive DB role/trigger was added), so direct database access could still alter it. Not claimed as tamper-proof.
- **Where audit writes happen**: for actions that already wrote their state change + a status-history row inside one `prisma.$transaction([...])` array (`updateInvoiceStatus`, `updateBookingStatus`, `updatePaymentStatus`, `updatePlanningRequestStatus`/`...Priority`), the audit record was added as a further array element — true atomicity (state change and its audit entry commit or roll back together) using an idiom already native to this codebase, no new infrastructure. `updateQuoteStatus` previously had *no* transaction at all (three bare sequential `await`s) — a pre-existing latent consistency bug, now fixed as part of wrapping it for the audit write. Standalone creation events (`createQuoteFromEnquiry`, `createBookingFromQuote`, `recordPayment`, the 6 PDF routes, the 3 email-send actions, the 2 portal planning-request actions) use a safe, never-throwing `recordAuditEvent()` wrapper instead, since there's no sibling business write to be atomic with.
- **Document storage provider**: none is configured (checked — no AWS/Cloudinary/Vercel Blob SDK or env vars exist in this project). `lib/documents/storage.ts` defines the seam (`DocumentStorageProvider` interface, a `noopStorageProvider` default) without inventing credentials or assuming a cloud service. `DocumentRecord.storageProvider`/`storageKey` stay `null` until a real provider is wired in; PDF generation and on-demand download are unaffected either way. **Local `.local-emails/`-style files are never treated as reliable production storage anywhere in this stage.**
- **Two new admin pages**: `/admin/documents` (filter by type/reference/related-record id) and `/admin/audit` (filter by entity/action/actor/date range) — both staff-only via the existing `proxy.ts` gate, no new auth code. No central email list was built (per Stage L2's own decision to use per-record status lines instead); Stage M follows that same precedent rather than duplicating it.
- **Client portal: no new access path.** `DocumentRecord`/`AuditEvent` are admin-visible only — clients keep using the exact same ownership-scoped L1 download routes as before. This is a deliberate reading of "clients may access only their own documents": the registry is a server-side generation log, not a new client-facing history feature.
- **Explicitly scoped out, not forgotten**: Consultation and standalone Enquiry status changes (not named in the stage's own action list; lower business-criticality than quote/invoice/payment/booking — can be added later following the identical pattern), and account-security events (login/logout/password-change — a different concern from business-record changes, arguably a future dedicated stage).
- **Residual gap**: `recordAuditEvent()`'s failure path only does `console.error` — this project has no Sentry/pino/winston, so a failed standalone audit write (rare; only possible if the database itself is unreachable at that moment) is only visible to someone tailing server logs.

## Online payments (Stage N)

Clients can pay an eligible invoice (status `ISSUED`/`PARTIALLY_PAID`, with an outstanding balance) online via Flutterwave, reconciled into the exact same `Payment` ledger manual payments already use — **no real Flutterwave merchant account or credentials exist for this project**; everything below was built and tested against a working mock provider (`lib/payments/mock-provider.ts`), never a real sandbox.

- **No second payment model.** `Payment` already had gateway-readiness fields reserved since Stage G (`provider`, `providerTransactionId`, refund fields) — this stage wires them up rather than inventing a parallel "payment attempt" table. A new nullable `Payment.invoiceId` ties an online payment to the specific invoice it was for; existing manual payments stay `invoiceId: null` (booking-level, exactly as before — zero behavior change there).
- **Overpayment guard is a dual cap, not a single one.** A booking can have multiple invoices, and manual payments are only ever booking-level (never invoice-tagged) — capping the payable amount at only the invoice's own online-payment history would let a client pay online for an invoice a manual payment had already covered elsewhere on the same booking. The amount due is `min(invoice-scoped outstanding, booking-scoped outstanding)`, computed by calling the existing `computePaymentSummary()` twice (`lib/payments/amount-due.ts`) — no new financial math, just applied to two correct slices of the same ledger.
- **Two hand-added partial unique indexes** (not expressible in Prisma's schema DSL, added directly to the migration SQL — see the comment on the `Payment` model in `schema.prisma`): one reference value can't be claimed by two online payments at once (manual payments' free-text references like "Cash" are unaffected), and at most one online payment can be in flight (`PENDING`/`PROCESSING`) per invoice at a time — this second index **is** the actual double-click/duplicate-attempt guard, enforced by an atomic `create()` + catch-conflict pattern (never a check-then-create race).
- **Webhook state machine**: only `PAID` is truly immutable. A `FAILED` payment can still be legitimately marked `PAID` later (Flutterwave allows retrying a failed attempt within the same checkout session), so `PENDING`/`PROCESSING`/`FAILED`/`CANCELLED` all remain open to a later verified success. One shared function (`lib/payments/apply-verified-outcome.ts`) is the only place a `Payment` is ever marked from a provider result — called identically by the webhook route and the client's checkout-return page, so there's exactly one state machine, not two. It never trusts a webhook payload or a return-page query string by itself; both always re-verify directly with Flutterwave first.
- **No automatic invoice-status transition.** A verified online payment updates the `Payment` ledger only — `Invoice.status` still only ever changes through the existing admin-only `updateInvoiceStatus` action, exactly matching this project's established philosophy ("PAID/PARTIALLY_PAID are admin-chosen transitions, not auto-derived from the payment ledger"). A passive "Last online payment: ..." line was added to the admin invoice page and the client's invoice page instead — informational only, never mutating anything.
- **Webhook authentication**: Flutterwave's v3 API echoes a merchant-chosen secret hash back in a `verif-hash` header for direct comparison (`crypto.timingSafeEqual`, not `===` — a plain string comparison is a timing side-channel on the secret). **Stated honestly, not assumed**: one secondary source claims Flutterwave's v4 API replaces this with an HMAC-SHA256 signature in a different header — this could not be confirmed without a real merchant account, so the check is isolated in its own function (`lib/payments/webhook-signature.ts`) that can be swapped without touching anything else.
- **Refunds are explicitly deferred, not simulated.** No real merchant account exists to verify a refund endpoint against, so none was built. Admin's existing manual refund fields (`refundAmount`/`refundDate`/`refundReference`/`refundReason`, already on `Payment` since Stage G) still let staff record that a refund happened by any means — nothing was removed.
- **Mock vs. production**: `getPaymentProvider()` uses the real Flutterwave implementation whenever `FLUTTERWAVE_SECRET_KEY` is set, and the mock otherwise — **except in production, where it throws rather than silently using the mock.** An email silently not sending (Stage L2's dev-mode fallback) is a low-stakes failure; a payment silently "succeeding" via a mock in production would not be, so this stage does not follow that same silent-fallback precedent.

## Production readiness, security & verification (Stage P)

A systematic production-readiness audit (four parallel read-only passes — authentication/authorization, payments/financial integrity, database/operational reliability, privacy/security — each with independent file:line evidence) found and fixed the following real defects. No live payment processing, no destructive database changes, and no new business workflow were introduced.

**Fixed, with regression coverage:**
- **Admin login had zero rate limiting and used a plain `!==` password comparison** (every other secret comparison in the codebase, including the Flutterwave webhook signature, uses `crypto.timingSafeEqual`). Fixed: `app/admin/login/actions.ts` now rate-limits (`10 attempts / 15 min` per IP, same `lib/rate-limit.ts` helper the Client Portal already used) and compares the password with a length-check-then-`timingSafeEqual` pattern.
- **The Flutterwave webhook returned `200 OK` even when *our own* call to Flutterwave's verify endpoint failed** (network error/timeout) — this suppressed Flutterwave's own retry mechanism for exactly the case it exists for, and no other job in this app re-verifies a stuck transaction. Fixed: `app/api/webhooks/flutterwave/route.ts` now returns `503` specifically when `verified.ok === false` (our-side failure), and still returns `200` for every provider-confirmed outcome (successful/failed/cancelled, including duplicates) — those remain correctly non-retriable.
- **The dual-cap overpayment guard (Stage N) was checkout-time only**, not re-checked when a payment is actually marked `PAID`. A narrow window (a stale ~30-minute-expired payment later resurrected `PAID` by a late webhook, alongside a second completed payment) could jointly overpay a booking with no visibility. Fixed: `lib/payments/apply-verified-outcome.ts` now re-checks the booking's outstanding balance at apply time and appends a `(WARNING: ... possible overpayment, needs manual review)` note to the audit summary when exceeded — it still never blocks the write, since the money is real and must be truthfully recorded, matching this module's existing philosophy for a voided-invoice conflict.
- **A conflicting-but-different "successful" event for an already-`PAID` payment** (a genuine provider-side double-charge) was recorded as an ordinary audit `SUCCESS`, indistinguishable from a routine duplicate-delivery no-op. Fixed: its summary is now prefixed `ALERT:` so it stands out when scanning the audit log. The `!verified.ok` audit entry (verification failures) is now also attributed to the known reference instead of `entityId: "unknown"`, making stuck/failed verifications searchable.
- **Three reference-number collision-retry loops were dead code.** `createBookingFromQuote`, `createQuoteFromEnquiry`, and `createInvoiceFromBooking` each had their own local `isUniqueConstraintError` copy checking only the classic `{target: string[]}` P2002 shape — but this project's Prisma 7 + `@prisma/adapter-pg` setup reports P2002 via `meta.driverAdapterError.cause.constraint.index` instead (discovered and correctly handled elsewhere, in `lib/email/outbox.ts` and `lib/prisma-errors.ts`, since Stage L2/N). The three local copies never matched, so a genuine `bookingNumber`/`quoteNumber`/`invoiceNumber` collision (low-probability, ~1.68M combinations/day, but non-zero) would throw instead of silently retrying. Fixed: all three now import the shared, correct `lib/prisma-errors.ts` helper.
- **Stage O's outstanding-balance figure didn't exclude cancelled bookings** (unlike its own booked-value figure right next to it) — a cancelled booking's full agreed total could appear as "money owed" in the portfolio-wide financial report. Fixed in `lib/analytics/financial.ts`; regression-tested against a fixture.
- **Quote and invoice line-item writes recomputed totals as a separate, non-transactional second write.** A crash between the item write and the totals recalculation could leave `Quote.subtotal`/`totalAmount` or `Invoice.subtotal`/`total` stale relative to the actual line items — self-healing on the next edit, but a real violation of the "recomputes automatically" guarantee for a document a client can view/pay against. Fixed: `addQuoteItem`/`updateQuoteItem`/`deleteQuoteItem` and their Invoice equivalents now wrap the item write and the totals recalculation in one `prisma.$transaction`.
- **`Booking` and `Invoice` had no indexes at all** beyond their primary/unique keys, and `Payment` had none on `createdAt` — confirmed live against the dev database to be hit, unindexed, by the admin bookings/invoices/payments lists and by Stage O's analytics queries. Added `@@index` on `Booking.status`/`eventDate`/`createdAt`, `Invoice.bookingId`/`status`/`createdAt`, and `Payment.createdAt` (migration `20261016104157_stage_p_add_missing_indexes` — pure `CREATE INDEX`, no data change, confirmed applied and present via `pg_indexes`).
- **PDF and CSV-export responses carried no explicit `Cache-Control`.** Both are authenticated, per-session data; relying only on Next's `force-dynamic` doesn't itself instruct a shared cache or a shared-device browser not to retain the response. Added `Cache-Control: private, no-store` to `lib/documents/render.ts`'s `pdfBufferToResponse` and `lib/analytics/csv.ts`'s `csvResponse` (both single shared helpers, so every PDF and CSV route picked this up for free).

**Confirmed correct, no change needed** (independently re-verified against the actual code, not assumed from a prior stage's report): webhook signature validation fails closed and is timing-safe; the mock payment provider refuses to run in production; out-of-order/duplicate webhook and return-page events are handled correctly (only `PAID` is immutable); the atomic create-and-catch-P2002 double-click guard for initiating an online payment is genuinely race-safe; no code path marks an invoice paid merely from checkout initiation; the `lib/payments/totals.ts` refactor from Stage O preserves its original behavior exactly; every Client Portal data loader re-derives ownership from the session (zero bare-`id` IDOR queries found across the whole portal); all client-portal security tokens (invite/email-verification/password-reset) are hashed at rest, single-use, and expiry-checked; no secret, password, or token is ever logged anywhere in the app; no debug endpoint, upload surface, or `dangerouslySetInnerHTML` exists anywhere; the Stage L2 dev-mode email-preview HTML-escaping fix is still in place; Stage O's analytics/CSV module exposes no client PII and is admin-gated purely via `proxy.ts`, same as every other admin route.

**Known, accepted limitations — require an owner/deployment decision, not a code fix** (documented here rather than silently fixed, per this project's standing rule against inventing unconfirmed business/infrastructure facts):
- **`lib/rate-limit.ts` keys on the client-supplied `X-Forwarded-For` header** with no built-in assumption about a trusted reverse proxy. If the production host doesn't strip/overwrite inbound `X-Forwarded-For` before the request reaches this app, an attacker can get a fresh rate-limit bucket on every request, defeating admin-login/client-login/registration/password-reset throttling entirely. **Before deploying, confirm your hosting platform's proxy strips client-supplied `X-Forwarded-For`** (Vercel and most managed platforms do this correctly by default; a custom reverse-proxy setup may not).
- **Session cookies are only ever sent `secure` when `NODE_ENV === "production"`** (correct), which means **the app must be served over HTTPS in production** — if it is deployed behind plain HTTP, or a reverse proxy that doesn't correctly terminate/signal TLS to Next.js, both admin and client-portal login will silently fail with no explanatory error anywhere in the app. Confirm HTTPS termination before launch.
- **No automated test suite or CI pipeline exists** (`package.json` has no `test` script; no `.github/workflows`). Every stage of this project, including this one, has been verified via one-off `scratch-verify-*.ts` scripts run manually and deleted afterward, plus manual real-HTTP checks — there is no standing regression gate before a deploy. Building one is a real future need but is itself a new-infrastructure decision, intentionally left to the owner rather than added unasked as part of this audit.
- **Date-range filters throughout the app (the Audit Log page and Stage O's analytics module) treat `from`/`to` as UTC day boundaries**, not a specific local timezone's day boundaries — no company operating timezone is configured or confirmed anywhere in this codebase. For a non-UTC timezone, this creates a constant boundary skew (e.g. a report for "today" can miss a few early-morning local records or include a few hours of the next calendar day). Not changed without a confirmed timezone, consistent with this project's rule against inventing unconfirmed business facts.
- **An admin-generated client-portal invite/reset token is passed back to the admin via a `?invite=` URL query parameter** for display/copying. It's single-use, hashed at rest, and expires in 7 days, so this isn't an auth bypass — but query strings are more exposure-prone (proxy/server access logs, browser history) than other channels. Left as-is (low severity, existing mitigations are solid); worth reconsidering if this flow is ever reworked.
- **An authenticated client changing their own profile email to one already registered to another client sees a differential "That email address is already in use" message** — a narrow, authenticated-only account-enumeration vector. Reviewed and deliberately left as-is: making this message generic would mean a client who mistypes their intended new email gets no useful feedback and never receives a confirmation link, with no way to tell why.
- **`apply-verified-outcome.ts`'s amount-mismatch check only rejects a verified amount *less than* expected**, not greater. Confirmed intentional, not an oversight: the verified amount always comes from Flutterwave's own API response, never from the untrusted webhook payload, so this isn't an attacker-exploitable path — flagged here only for the owner's awareness.

### Permissions — EDITOR is defined but not usable yet

`AdminRole` has two values (`ADMIN`, `EDITOR`), but **every one of this app's 13 existing admin feature areas** has **zero in-action role checks** — they rely entirely on `proxy.ts`'s page-level gate, which only recognizes the one shared admin password, not individual accounts or roles. Deny-by-default for EDITOR holds **only because the new login flow is unreachable this phase** (no route calls `lib/admin/auth.ts`), not because any route actually enforces role. Do not treat `EDITOR` as a safe, limited role until the cutover below is complete and each admin area has been individually reviewed. **Hiding a navigation link is never authorization** — `app/admin/(dashboard)/layout.tsx`'s nav is a flat, role-unaware list today, and even a role-aware version of it would only hide a link, not block direct navigation to the URL or direct Server Action invocation. ### Role-check API fix (CMS Phase 1.4)

`lib/admin/auth.ts`'s `requireAdminRole(role)` originally did an **exact** match (`admin.role !== role`), which — with only two roles — meant `requireAdminRole("EDITOR")` would have incorrectly denied an `ADMIN` too, since `"ADMIN" !== "EDITOR"`. Not exploitable in practice (every call site only ever passed `"ADMIN"`), but ambiguous and a latent foot-gun for the first future EDITOR-permitted action. Fixed with a new `lib/admin/role.ts` exporting `hasAtLeastRole(actual, minimum)` — a rank-based (`ADMIN` > `EDITOR`) minimum-permission comparison, pure and dependency-free (no database or Next.js import, unit-tested directly in `scripts/verify-cms-phase1-security.ts`). `requireAdminRole(minimumRole)` now means "this role or anything above it," unambiguously, at every call site, with no call-site changes required (`requireAdminRole("ADMIN")` behaves identically to before, since nothing outranks `ADMIN` yet).

### Login, logout, session, proxy

- `app/admin/login/actions.ts` — email+password against the `Admin` table, `verifyAdminPassword()` (Argon2id). ## Deploying

### Database migrations on deploy (Vercel)

`package.json` has a `vercel-build` script — Vercel auto-detects and runs this instead of `build` for Next.js projects, no dashboard configuration needed: `if [ -n "$DATABASE_URL_UNPOOLED" ]; then DATABASE_URL=$DATABASE_URL_UNPOOLED prisma migrate deploy; fi && next build`. This applies any pending migrations to the production (Neon) database on every deploy, before the app itself builds, so a deploy can never ship code that reads from tables that don't exist yet.

It runs against `DATABASE_URL_UNPOOLED` specifically, not the normal pooled `DATABASE_URL` the running app uses — Prisma's migration engine uses advisory locks that pooled connections (PgBouncer-style, which Neon's default pooled endpoint uses) don't reliably support. Vercel's Neon integration adds `DATABASE_URL_UNPOOLED` automatically when connected; confirm it's present in the project's Vercel environment variables before relying on this. `prisma migrate deploy` is idempotent — it only applies migrations not already recorded, so running it on every deploy (including ones with no new migrations) is safe and a no-op.

**Preview deploys**: if `DATABASE_URL_UNPOOLED` is only set for the Production environment (the usual setup), a Preview build (any branch other than the one tied to Production) skips the migration step entirely instead of failing — the `if [ -n ... ]` guard means an unset variable just means "don't migrate here," not a broken build. Preview builds run against whatever schema already exists; they never attempt to migrate an environment this script can't positively identify.

This only affects Vercel deploys — local `npm run build`/`npm run dev` are unchanged and still use the plain local `DATABASE_URL`.

Standard Next.js app — deploys cleanly to Vercel, Netlify, or any Node hosting, **over HTTPS** (session cookies are `secure` in production — see Stage P above). Requires the environment variables above (`DATABASE_URL`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, `CLIENT_SESSION_SECRET`, `NEXT_PUBLIC_APP_URL`) to be set on the host — plus the `emailVerifiedAt` backfill noted above if any clients were activated before Stage K.5, `RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` (Stage L2) if you want email actually delivered rather than written to local files, and `FLUTTERWAVE_SECRET_KEY`/`FLUTTERWAVE_SECRET_HASH` (Stage N) before online payments can process anything beyond the mock provider — including completing real Flutterwave merchant onboarding and a live webhook delivery test, neither of which has been done in this environment. Stage M adds no new required environment variables — persistent document storage is an optional future addition (see `lib/documents/storage.ts`). Confirm your host's reverse proxy strips inbound `X-Forwarded-For` before relying on this app's rate limiting (see Stage P above).
